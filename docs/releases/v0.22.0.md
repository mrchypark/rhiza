# Rhiza 0.22.0

## Managed HA reference runtime

This release adds the Go managed SQL reference runtime and v1alpha2 recovery
components for Deployment-based HA with no PVCs. Two init containers prepare a
Pod identity and wait for the committed bootstrap plan before the main process
opens the managed database. Quorum-backed voter replacement restores a prepared,
read-only view, admits the exact registered learner, and completes replacement
only after the committed membership and live authority agree.

Recovery preserves immutable origin, adoption, and voter identity evidence
across a main-container restart. A committed ADD whose finalization failed can
resume without repeating REMOVE. Internal peer learning no longer depends on
client SQL readiness; live authority and membership checks remain mandatory.
Uncertain pending writes remain fail-closed.

The qualified path uses the private managed runtime profile and reference host.
The general public operator recovery engine remains unavailable; these results
do not establish arbitrary embedded-application recovery or a general-purpose
disaster-recovery service. HA storage is append-only: online deletion GC is not
supported by this managed path.

## Compatibility

HA resources serve and store v1alpha2 only. There is no v1alpha1 conversion or
migration path. Use an explicitly provisioned, isolated deployment and storage
binding; missing authority is an error, not permission to bootstrap over an
existing archive. Preserve recovery evidence when any check refuses startup.

This release does not replace the existing Local init-container recovery
procedure or remove its ownership, durability, and archive compatibility
conditions. The [Local contract](../embedded-object-storage.md) and
[init-container guide](../local-init-container-recovery.md) still apply. The
Rust package version tracks the release; the new managed reference runtime is
implemented in Go.

[v1alpha2 contract](https://github.com/mrchypark/rhiza/actions/runs/41201108949),

must also satisfy the normal merge and publication checks.

Actual kubelet checks covered a new replacement Pod UID, a subsequent main
restart within that replacement Pod, unchanged origin/adoption/voter identity,
two completed init containers, no PVC volumes, and acknowledged SQL readback.
S3, GCS, and Azure contracts each passed five checks through their actual
adapters against pinned emulators, with no failures or skips. Run-owned test
resource cleanup was verified.

These results do not qualify live cloud parity, Chaos Mesh faults, network
isolation, isolated-process physical fencing, operator-managed Service
ownership, or a kubelet restart after a later recovery-operation rollover.
Post-release Kubernetes Chaos Mesh results must be reported separately; they are not
asserted by this release note.
