# Rhiza 0.22.1

## Managed Rust HA and recovery corrections

This release connects the additive Rust `ManagedDb` and `ManagedOpenConfig`
API to the verified Go managed SQL Host through `RhizaOpenManaged` in the C
ABI. Existing `Db` APIs and C symbols remain available. Managed operations
retain live authority, generation and exact pending-request checks; unknown
outcomes remain fail-closed rather than becoming replacement SQL submissions.

The changes since v0.22.0 include PRs #258–#266:

- Managed Rust startup, SQL, pending recovery, readiness and lifetime handling
  through the C ABI, with actual Rust/Go FFI contract tests.
- Certified checkpoint restore on normal startup, exact pending SQL recovery
  across hosts, and reconciliation when a peer already finalized the original
  durable receipt. Recovery does not resubmit SQL or infer success from a
  missing reservation alone.
- Reproducible, scoped Chaos Mesh qualification, one-shot fault cleanup,
  same-client-Pod Service readiness prerequisites and bounded failure evidence.
- Local filesystem Upload/Delete serialization across the entire provider
  mutation lifetime, including checksum and cleanup work, plus deterministic
  mutation-contention regression tests.

## Compatibility

Use the native archive from **v0.22.1** with the v0.22.1 Rust crate. The new
managed ABI symbol is not present in v0.22.0 archives; do not mix an older
`RHIZA_NATIVE_LIB_DIR` archive with this crate. The packaged crate also contains
the matching Go source snapshot for builds using the Go toolchain.

A custom managed startup checker that supports pending SQL recovery must also
implement `node.ManagedSQLRecoveryChecker`. If an original SQL outcome needs
certified recovery and this checker is absent, recovery refuses safely; the
missing capability does not authorize a new write or clear uncertainty.

Managed HA remains the explicitly configured v1alpha2 Deployment/reference
runtime path with NoPVC, immutable origin/adoption evidence and append-only
object storage. Online deletion GC is not supported for this HA path. This
release does not make the general public operator recovery engine available
or introduce v1alpha1 conversion, archive migration or arbitrary application
recovery. The existing Local backup and init-container contracts still apply.

## Verification and limits

Source `b3b36575f07dda6e886916b5a0a84617c680ed7f` passed the
[full CI](https://github.com/mrchypark/rhiza/actions/runs/41325791502),
[managed bootstrap](https://github.com/mrchypark/rhiza/actions/runs/41325791493),
[provider qualification](https://github.com/mrchypark/rhiza/actions/runs/41325791478)
and [v1alpha2 contract](https://github.com/mrchypark/rhiza/actions/runs/41325791431)
workflows. This evidence precedes the release metadata change; the final
release commit must separately pass the normal merge and packaging checks.

An isolated local k3s run using pinned Floci S3 and Chaos Mesh verified actual
Pod replacement and a subsequent same-Pod container restart, NoPVC, certified
identity handling, Rust `ManagedDb` → C ABI → Go Host operation, ACK readback
and a new committed write. Its exact source was
`4958acf409d75e52b0f14bd6270b9bfbcad25e7d`; the later Local-only filesystem
owner correction does not run on that HA/S3 path. The full later release SHA
was not separately subjected to this Chaos run. Test-owned resources and
temporary authentication were cleaned up; prior failed attempts and unknown
historical causes remain preserved rather than being replaced by a retry.

The first post-merge CI on `4958acf` failed in Local maintenance with an
`xattr.Set` ENOENT for `local-gc-control.swap`. A real-provider controlled
mutation-lifetime failure was reproduced and the owner serialization fixed;
the exact historical CI interleaving was not proven. PR #266 and the final
`b3b3657` CI passed without rerunning the failed CI to erase that evidence.

**Performance non-regression is not established.** The
[final main Performance workflow](https://github.com/mrchypark/rhiza/actions/runs/41325791507)
completed its correctness guards with zero failed writes and verified ACKs,
but its within-run before-ACK three-sample medians showed throughput **−4.11%**
and p99 **+37.38%** versus `4958acf`. The cause remains unproven; workflow
SUCCESS is not a relative performance guarantee. Earlier negative observations
are retained. This server/S3 benchmark does not measure Local filesystem
mutation-gate performance.

Live GCS/Azure parity, network partitions, physical node fencing, whole-quorum
loss, performance targets and all application/SDK operation combinations are
not qualified by these results. Emulator adapter contracts and a
quorum-preserved local Chaos run must not be presented as those guarantees.
