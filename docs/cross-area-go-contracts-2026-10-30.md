# Go 영역 간 계약 허브 — 통합 경계 검토 완료

## C0. 상태와 기준

상태는 **보정·독립 통합 경계 검토 완료(지정 범위 한정)**다. 고유 Blocker/Major 지적 16건을 보정했다. A의 E01–E08/E17 및 해당 C7 조항은 내용이 유지된 상태에서 R3/R4 소스 검토의 추가 지적이 0건이었다. 최종 동일한 규범 snapshot을 대상으로 한 두 독립 병렬 검토 batch R6/R7에서는 B의 E09–E16·관련 제한 검사와 C의 전체 흐름 이해도 검토 모두 Blocker/Major가 0건이었다. R7-C의 Nit 1건은 E03 Append 소스 URL을 실제 선언 위치 `wal.go:662`로 보정했다. 이는 직렬 전체 5단계 인증이나 전체 엔진 감사가 아니다. [통합 검토 기록](cross-area-go-egm-review-2026-10-30.md)과 [원본 검토 증거](cross-area-go-review-evidence-2026-10-30.md)를 함께 확인한다. 이 문서는 현재 구현의 직접 연결 계약을 설명하며 새로운 런타임 동작을 요구하지 않는다. 각 엔진의 내부 알고리즘과 전체 wire schema는 소유 영역의 본문·부록을 따른다.

연결 기준은 `008f8e576ad76425182e10a69b987f10cfb48b2a`다. QuePaxa 원문과 과거 검토·실행 기록의 기준 `8acb6da35a4c6fc83fa14ecec2fe2b64370fa4bd`는 그대로 유지한다. 부모가 전달한 baseline 비교 결과에서 두 기준 사이 비문서 차이는 없었다. 따라서 기준 차이 자체를 의미 변경으로 취급하지 않는다. 이 허브와 원문의 명시적 연결 보정은 현재 기준의 overlay이며, 과거 감사를 현재의 전체 통합 감사로 바꾸지 않는다.

근거는 [색인](reverse-spec-index-2026-10-30.md)의 11개 본문과 연결 부록, 필요한 호출 지점의 소스 판독, 부모가 전달한 초기 W/S/L 검토 결과다. 아래 표의 coverage는 실제 연결을 문서화했다는 뜻이다. 실행 시험, 전체 엔진 감사, 재구현 동등성 또는 전체 EGM 승인을 뜻하지 않는다. 이번 작성자는 빌드·테스트·서버·emulator를 실행하지 않았다. S-01/S-02의 장애 결과도 정적 도출이며 실행 재현 결과가 아니다. 역사적 EGM 기록과 검증 기록은 수정하지 않는다.

## C3. 대표 흐름: SQL 쓰기에서 복구 가능한 checkpoint까지

다음은 object storage가 설정된 HA의 `before-ack` 경로다. Local 경로에는 C6의 별도 실패 제한이 있다. 유효한 durability 문자열은 `async`와 `before-ack`이며 `before_ack`는 열기에서 거절된다.

1. HTTP SQL handler 또는 FFI `execute`가 공통 Go mutation API를 호출한다(E01). HTTP는 body 제한도 적용한다. 공통 API는 writable/Ready·context·charge·reservation·clone·SQL validation·fingerprint/encoding·request stripe를 거친다. retained 동일 intent면 새 proposal 없이 E17로 간다.
2. batch owner가 request를 받아 encoded 값을 Core에 제안한다(E02). recorder가 값과 ISR을 기록·Sync하고 summary quorum을 만든다(E03/E04). 인증된 결정, 연속 Core tip, 전파 완료는 각각 다른 상태다. `ProposeCertified`만의 성공을 일반 `Propose` 완료로 바꿔 해석하지 않는다.
3. 운영 Learned 수신자는 결정을 설치하고 그 slot까지 materializer에 순서대로 apply한 뒤 ACK한다(E04/E05). 호출자 쪽도 apply 후 receipt를 얻는다. SQL의 결정적 실행 거절은 `status:"rejected"` receipt를 반환할 수 있다. HTTP 200 또는 FFI `data`는 application 성공을 대신하지 않는다. SQL `Applied`의 false 기본값을 KV/graph의 적용 의미와 동일시하지 않는다.
4. server는 설정된 durability barrier를 기다린 뒤 mutation 응답을 완료한다. receipt가 먼저 materialize되므로 병행 `request_status`가 committed를 보았어도 이 barrier 완료는 증명하지 않는다. caller cancel이 먼저 도착하면 작업이 계속되는 동안 `commit_unknown`이 반환될 수 있다. 같은 ID와 같은 intent의 in-window mutation retry는 barrier를 다시 기다린다(E17).
5. 이후 checkpointer는 같은 tip의 SQLite/graph snapshot을 받아 후보 root를 생성한다(E06/E07). 파일 업로드나 후보 생성만으로 certified CURRENT가 되지 않는다. validator와 prepare, seal decision, 결정 archive 내구성, CURRENT 승격을 구별한다(E08).
6. 복구는 보호된 archive/root와 검증된 base를 사용하여 결합 store를 설치하고 연속 suffix를 replay한다(E10/E11). Core compaction과 GC는 별도 작업이며 authoritative base와 보존 집합이 필요하다. QLog manifest 전환 오류는 C6처럼 부분 전환을 남길 수 있다(E12). 응답, snapshot, archive, restore, compaction을 하나의 원자 transaction으로 보장하지 않는다.

## C4. 취소·오류·재시도·자원 소유권

제출 전 context 오류와 제출 후 결과 불명은 구별한다. `CommitUnknownError.Unwrap`은 `ErrCommitUnknown`과 context 원인을 함께 노출할 수 있다. FFI는 `commit_unknown`을 `timeout`/`canceled`보다 먼저 매핑한다. HTTP는 별도 status/JSON code 규칙을 사용한다. 두 adapter가 같은 Go 오류를 받는다는 이유로 envelope나 상태코드가 같지는 않다. [FFI Go API](c-ffi-go-contracts-2026-10-30.md#go-api-signatures-and-behavior), [HTTP errors](request-http-go-contracts-2026-10-30.md#실패-envelope와-status).

worker로 넘어간 admission lease와 proposal/batch context는 caller 대기와 수명이 다르다. batch job은 독립 30초 context, direct proposal은 최초 registration deadline과 30초의 최솟값을 사용한다. QLog API에는 context가 없다. archive batch는 한 caller 취소 뒤에도 manager context의 5분 작업을 계속할 수 있다. timeout은 underlying storage goroutine 종료나 mutation 부재를 증명하지 않는다.

retry 보호는 retained window 안의 동일 request ID/intent에 한정된다. 기본 window 65,536에서 `retry_through_slot=slot+65,536-1`이며 material tip이 이 값과 같을 때까지 retained다. 그 뒤 `unknown_or_expired`는 진행 중·미제출·만료를 구별하지 않는다. SQL/KV/notify replay dedup과 graph fingerprint 비교의 차이는 [materializer](materializer-go-reverse-spec-2026-10-30.md#encoded-decided-values)의 현재 제한으로 유지한다.

snapshot cleanup은 capture 호출자, 반환 reader Close는 reader 소비자, pin 갱신/종료는 pin owner, C response buffer의 `RhizaFree`는 C caller의 책임이다. ordinary `Shutdown`은 writer 종료 뒤 Local filesystem owner가 있을 때 mutation drain을 수행한다. owner 없는 HA shutdown은 이 drain 없이 bucket을 닫으므로 성공 반환이 mutation 결과 확인을 뜻하지 않는다. 별도 `TerminalDrain`은 bucket을 보관하고 `shutdownEngine(false)` 뒤 그 bucket을 background context로 drain/close하며 join한 오류가 없을 때만 exact cluster/node/WAL에 묶인 `StorageKnown`을 설정한다. caller timeout은 이 절차를 중단하거나 완료를 증명하지 않는다. Bucket lifetime의 clean drain도 process termination/recreation prevention을 증명하지 않는다. filesystem-owner poison은 잠금을 남길 수 있고 owner close 실패 뒤에도 qlog lock release를 시도하므로 두 잠금의 수명은 다를 수 있다(E16).

## C5. 복원·fencing·세대 전환의 신뢰

ordinary checkpoint 복구는 seal/certified decision, prefix, membership, validator와 object content 검증을 연결한다. archive Load만으로 quorum 인증이 완료되지 않는다. 저장 certificate에는 recorder별 서명이 없고 peer TLS 인증에 의존하므로 독립 서명 증명으로 해석하지 않는다. `InstallFencedGenerationBase`는 fresh target WAL에 적용하는 외부 관리 신뢰 전환이며 caller의 anchor 검증이 전제다.

immutable `recovery/anchor.json`은 fork source와 target lineage를 연결한다. 외부 application anchor는 별도 live record다. `Activate`는 빠진 anchor를 bootstrap하지 않는다. record 검증 뒤 exact already-committed 요청이면 저장 receipt를 먼저 반환한다. 이 committed 검사는 현재 `PendingWrite`를 검사하지 않으므로 ordinary application update가 pending write를 남긴 뒤에도 해당 retry가 성공할 수 있다. 이 fast path가 아닌 새 전환 또는 미완료 전환의 시작·재개에서는 application `PendingWrite`를 거절한 뒤 `Transition`을 예약·재개하고 원래 evidence/source/generation을 고정한다. `PendingWrite`를 복구 예약 필드로 사용하지 않는다. RequestHash는 FenceHash를 포함한 전체 요청에 결합한다.

operator는 저장된 request를 현재 operation·fork·target membership·fence assertion에서 재구성한 요청과 대조하고 Starting/Restarted에서 receipt를 live backend로 Verify한다. successor StatefulSet PUT 직전에도 검증한다. Verify는 exact request hash와 receipt, live target binding/generation 및 완료된 transition을 확인한다. Verify도 같은 committed predicate를 사용하므로 pending application write가 없다는 증명은 아니다. 저장 receipt만으로 활성화하거나 이후 write 권한을 cache할 수 없다. 일반 application 작업의 `CheckBinding`은 별도로 live binding/generation, pending transition과 `PendingWrite`를 검사한다. receipt verification은 이 application authority 검사를 대체하지 않는다. [Operator boundary](operator-go-contracts-2026-10-30.md#environment-archive-and-anchor-contracts), [controller](https://github.com/mrchypark/rhiza/blob/8acb6da35a4c6fc83fa14ecec2fe2b64370fa4bd/pkg/operator/controller.go#L455), [coordinator](https://github.com/mrchypark/rhiza/blob/8acb6da35a4c6fc83fa14ecec2fe2b64370fa4bd/pkg/recoveryanchor/coordinator.go#L95).

manual fence gate는 operation/source/StatefulSet UID와 확인·evidence를 받는 신뢰 assertion이다. automatic proof의 exact captured scope 검증과 동일하지 않다. clean terminal drain은 cluster/node/WAL 및 storage-known에 한정된다. Pod 삭제 응답이나 Ready만으로 전체 process 종료·재생성 방지·outstanding storage 해소를 추론하지 않는다. learner Ready도 voting authority가 아니다.

독립 attestation의 timestamp 검사는 일반적인 freshness 검사와 다르다. top-level `ObservedAt`와 barrier `DeniedAt`는 nonempty만 확인한다. storage의 before/after 시각은 RFC3339로 parse한다. 선언된 `QuietWindowSeconds`는 int 값으로 30 이상이어야 하지만 elapsed 조건은 정확히 `after.Sub(before) >= time.Duration(QuietWindowSeconds)*time.Second`다. signed 64-bit duration 변환·곱셈의 overflow를 검사하지 않으므로 elapsed가 선언된 초 또는 30초 이상이라고 항상 보장하지 않는다. 64-bit target에서 선언값 `2^62`는 곱셈이 0으로 wrap하여 다른 조건이 맞으면 같은 before/after 시각도 통과할 수 있다. 이 예는 정적 도출이며 실행하지 않았다. 종료 시각은 `now+2분` 이하를 요구하지만 최대 과거 나이는 검사하지 않는다. 별도의 ledger hash/Pod inventory 재확인은 scope 변경을 막는 검사이며 observation-age 검사가 아니다. 정확한 조건은 [operator attestation 계약](operator-go-contracts-2026-10-30.md#independent-attestation-contract)을 따른다.

## C6. 초기 검토에서 확인한 현재 제한

**S-01: Local checkpoint 재발행의 portable identity 충돌.** 처음 block key가 없으면 portable descriptor가 generation 0 block을 참조할 수 있다. snapshot metadata를 seal-root 키에 게시한 뒤 compaction 전에 중단되면 prepared resume이 portable checkpoint를 다시 만든다. 이미 있는 기본 block key는 generation 1 fallback을 유발하고 file/portable root hash를 바꿀 수 있다. Local seal root가 같아도 `PortableRoot`가 달라져 immutable metadata의 exact readback에서 `Local snapshot publication mismatch`가 반환된다. block과 metadata가 원격에 남으므로 reopen만으로 이 조건이 사라지지 않는다. 성공하는 retry나 자동 repair를 보장하지 않는다. [Checkpoint §8](checkpoint-go-reverse-spec-2026-10-30.md#8-local-경로), [Archive Local 계약](archive-recovery-go-reverse-spec-2026-10-30.md), [Node Local 계약](node-lifecycle-go-reverse-spec-2026-10-30.md#local-quiescence-and-recovery-evidence). 이 시나리오는 정적 도출이며 실행하지 않았다.

**S-02: QLog 선택과 live Core floor의 부분 전환.** compaction manifest rename 후 directory Sync가 실패하면 QLog는 새 generation/segment 목록을 채택하고 fatal uncertainty를 보존한 채 오류를 반환할 수 있다. Core는 `compaction.Commit` 오류에서 즉시 반환하여 base/floor를 설치하지 않는다. 따라서 QLog는 compacted generation을 선택했지만 live Core는 이전 floor/retained state를 노출할 수 있다. completed QLog 작업의 deferred Abort는 이를 되돌리지 않는다. 실패가 old WAL 선택 보존을 뜻하지 않으며 manifest 선택·내구성 확인·Core 설치를 각각 구별하여 재개방 검증을 따라야 한다. [QLog compaction](qlog-go-reverse-spec-2026-10-30.md), [QuePaxa durability](quepaxa-go-durability-evidence-2026-10-30.md). 이 연결 결과도 정적 도출이며 실행하지 않았다.

보정과 독립 재검토의 범위·판정은 [통합 검토 기록](cross-area-go-egm-review-2026-10-30.md), 각 검토자의 실제 읽기 범위와 원문은 [검토 증거](cross-area-go-review-evidence-2026-10-30.md)를 따른다. 고유 Blocker/Major 16건은 원문과 연결 계약에 반영했으며 중복 지적은 별도 결함으로 세지 않았다. S-01/S-02는 구현을 고친 결과가 아니라 현재 구현의 제한을 명세에 보존한 결과다. E01–E17과 C7의 직접 owner/source 연결에 한정한 문서 검토이며 코드 변경이나 새로운 runtime test 통과를 뜻하지 않는다.
