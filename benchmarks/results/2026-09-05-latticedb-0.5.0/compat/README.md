# LatticeDB v0.3.0 to v0.5.0 persistence compatibility

## Result

Passed on 2026-09-05 with Go 1.27.0 on darwin/arm64.  Two binaries were built
from the same Rhiza source using alternate module files:

| Binary | `github.com/mrchypark/latticedb-go` |
| --- | --- |
| writer | v0.3.0 |
| reader | v0.5.0 |

The run performed these transitions against the same data directory:

1. v0.3 wrote a SQLite table/value, a KV key/value, a graph node/value, and
   recorded the corresponding SQL, KV, and graph request receipts.
2. v0.5 reopened that directory, read all values, and verified each old
   receipt is `committed`.
3. v0.5 added one value in each of SQL, KV, and graph, then a v0.5 restart
   verified both generations and all v0.5 receipts.
4. The v0.3 binary reopened the resulting v0.5-written directory and verified
   both generations and their receipts.

Checkpoint recovery also passed.  The v0.3 writer used the filesystem object
store with before-ack durability and closed cleanly.  Its shutdown created,
published, and prepared a streaming checkpoint at slot 6.  The resulting
`checkpoint/CURRENT` was:

```json
{"index":6,"root_hash":"2e8c06e2dc7e95e4031f47c6601aec566b6bca58044384fefab8730a5445cd52"}
```

A v0.5 reader opened a fresh data directory against that archive and recovered
the v0.3 SQL/KV/graph values and receipts.

## Reproduce

The runnable harness is this directory's `main.go` and `run.sh`. From the
Rhiza repository root:

```sh
benchmarks/results/2026-09-05-latticedb-0.5.0/compat/run.sh \
  "$PWD" \
  /tmp/rhiza-lattice-050-eval/work \
  /tmp/rhiza-lattice-050-eval/baseline.mod
```

The script copies the old and current module definitions into its working
directory, so dependency checksums generated by `-mod=mod` stay outside the
repository. It creates unique temporary data/object-store directories and does
not run a benchmark.

The full captured output is in [output.txt](output.txt). The successful
output was:

```text
writer: SQL/KV/Graph writes and receipts verified
reader: old values/receipts verified; v0.5 writes committed
reopen: old/new SQL/KV/Graph values and receipts verified
reopen: old/new SQL/KV/Graph values and receipts verified
checkpoint writer: close will archive and certify a checkpoint
creating streaming checkpoint at slot 6
checkpoint candidate published: index=6 size=42722 files=2
checkpoint prepared: index=6 root=2e8c06e2dc7e95e4031f47c6601aec566b6bca58044384fefab8730a5445cd52
checkpoint reader: v0.3 archive/checkpoint recovered into fresh v0.5 data directory
```

## Scope and limits

This is a single-node, clean-shutdown compatibility check. It establishes the
tested Rhiza SQL/KV/graph materialized state, request receipts, filesystem
archive, and certified checkpoint can cross these versions in both direct-data
and v0.3-checkpoint-to-v0.5 recovery paths. It does not establish an upstream
LatticeDB format-compatibility contract, multi-node recovery behavior,
interrupted-write recovery, or cloud object-store compatibility.

Rhiza has no public standalone checkpoint export/restore API; the checkpoint
case therefore uses the existing embedded `Open` recovery path and a filesystem
object store.
